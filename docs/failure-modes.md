# Failure modes

Every row is a way the system could go wrong, how the design prevents it, and
the test that proves it. The numbers match the adversarial test list in
CLAUDE.md section 11. Rows are added as each test is built; only tested
protections are listed here.

| # | Failure | What breaks | How this design prevents it | Test |
|---|---|---|---|---|
| 15 | Someone registers and asks to be an admin (`"role": "ADMIN"`, `is_admin`, and so on) | An attacker gets admin powers, such as creating or deleting events | The register request rejects unknown fields (422); `register_user()` has no `role` parameter and always sets `USER`; the DB column defaults to `USER` with a CHECK allowing only USER/ADMIN. Admins come only from a separate CLI (S1.6). | `tests/adversarial/test_15_self_registration_cannot_create_admin.py` |
| - | Two sign-ups with the same email at the same moment | Two accounts for one email; a later login is ambiguous | No check-then-insert. The `uq_users_email` UNIQUE constraint decides atomically, and the loser gets a typed `UserAlreadyExists` (409). | `tests/integration/test_register.py::test_ten_simultaneous_signups_with_one_email_create_exactly_one_user` |
| - | A user edits their token to say `"role": "ADMIN"`, or signs their own, or sends `alg: none` | Anyone becomes admin | Tokens are HS256-signed with a secret only the server knows; `decode_access_token` pins `algorithms=["HS256"]`, requires every claim, and checks `type == "access"`; any failure is a 401 with no detail | `tests/unit/test_tokens.py` |
| - | A stolen access token is used later | The thief acts as the user indefinitely | Access tokens expire after 15 minutes (`exp` is checked on every request) | `tests/unit/test_tokens.py::test_an_expired_token_is_rejected` |
| - | An attacker uses login to discover which emails are registered | Targeted phishing or password guessing | An identical 401 body for "no such email" and "wrong password", and similar timing, because unknown emails are still checked against a dummy hash (measured 73 vs 74 ms) | `tests/integration/test_login.py::test_wrong_password_and_unknown_email_get_the_identical_401` |
| - | A refresh token is stolen and used by an attacker | The attacker stays signed in for days | Refresh tokens are single-use and rotated; presenting an already-used token revokes the whole family, so the attacker and the real user are both signed out at the next refresh. Only SHA-256 hashes are stored. | `tests/integration/test_refresh.py::test_reusing_an_old_refresh_token_revokes_the_whole_family` |
| - | The same refresh token is sent several times at once (race) | Several valid token chains branch from one token | Claimed by one conditional `UPDATE ... WHERE used_at IS NULL ... RETURNING`; exactly one request wins | `tests/integration/test_refresh.py::test_five_simultaneous_refreshes_with_one_token_succeed_only_once` |
| - | A user logs out but their refresh token is reused | Logout is cosmetic | Logout revokes the token family in the DB | `tests/integration/test_refresh.py::test_logout_revokes_the_refresh_token` |
| - | A regular user calls an admin route (create, edit or delete an event) | Anyone can create fake events or cancel real ones | `require_admin` checks the token's role and returns 403; no token returns 401. Admins can only be created by `scripts/seed_admin.py`, never over HTTP | `tests/integration/test_events_admin.py::test_a_regular_user_gets_403_on_every_admin_route` |
| - | An admin deletes an event that is already on sale | Sold tickets point at a deleted event | Only DRAFT events can be deleted (409 otherwise); published events can only be CANCELLED. Tiers have no ON DELETE CASCADE | `tests/integration/test_events_admin.py::test_a_published_event_cannot_be_deleted_only_cancelled` |
| - | A cancelled event is re-opened, or two admins change status at the same moment | Sales resume on an event customers were told was cancelled | One-way status rules (DRAFT -> PUBLISHED -> CANCELLED, CANCELLED is final), checked while the event row is locked with `SELECT ... FOR UPDATE` | `tests/integration/test_events_admin.py::test_status_moves_forward_draft_published_cancelled` |
| - | The public sees unpublished (DRAFT) events | Unannounced events leak early | Lists only show PUBLISHED, upcoming events; a draft's detail page returns the same 404 as a nonexistent id | `tests/integration/test_events_public.py::test_drafts_and_unknown_ids_are_both_404` |
| - | A search for `%` or `_` acts as a wildcard | Searches return wrong results; scanning everything is easy | User text is escaped before `ILIKE ... ESCAPE '\'`, so wildcards are matched literally | `tests/integration/test_events_public.py::test_wildcard_characters_are_searched_literally` |
| - | A client asks for a huge page | One request loads every row; slow responses, memory pressure | `limit` is capped at 100 and `offset` at 10,000 (422 otherwise) | `tests/integration/test_events_public.py::test_out_of_range_paging_is_rejected` |
| 1 (part) | Many buyers race for the last seats (Redis layer) | More holds than seats | `reserve_tier.lua` checks and decrements in one atomic Redis step. 500 simultaneous buyers (1-3 seats each) on 50 seats never reserve more than 50, every seat is accounted for, and every refusal is SOLD_OUT. The HTTP + 3-replica version of test 1 comes in S2.9 / S8.1 | `tests/integration/test_reserve_tier.py::test_500_simultaneous_buyers_never_take_more_than_50_seats` |
| - | A multi-seat request gets only part of what it asked for, or a refused request leaves debris | Partial holds, leaked inventory | All checks happen before the first write; refused requests leave Redis byte-for-byte unchanged (snapshot compared) | `tests/integration/test_reserve_tier.py::test_asking_for_more_than_is_left_takes_none_of_them` |
| 12 (part) | A missing inventory counter is treated as zero (or as plenty) | Sales stop wrongly, or oversell | The script returns NOT_INITIALISED (-2) and does **not** create the key; rehydrating from the DB comes in S2.8 | `tests/integration/test_reserve_tier.py::test_a_missing_counter_is_not_treated_as_zero` |
| - | A burst of requests exhausts the Redis connection pool | Instant errors during a sale | A blocking pool: requests wait up to 5 s for a free connection | The 500-buyer test above uses the app's `build_redis_client` |
| 1 (HTTP, 1 replica) | Many users race over HTTP for the last seats | Oversell through the API | Same atomic script behind the endpoint; 300 simultaneous HTTP hold requests on 50 seats give exactly 50 x 201 and 250 x 409 sold_out, and the counter ends at 0. The 3-replica version comes in S8.1 | `tests/integration/test_holds_api.py::test_300_buyers_over_http_get_exactly_50_seats` |
| - | A client puts someone else's user id in the request | Holds charged to another account | The hold's user comes only from the access token; the body has no user field (`extra="forbid"`) | `tests/integration/test_holds_api.py::test_a_hold_is_created_for_five_minutes` |
| 6 (holds) | A client retries "hold seats" (timeout, double-click, flaky network) | Two holds, twice the seats taken | `Idempotency-Key` header; an atomic `SET NX` claim, then a stored answer replayed for 24 h; concurrent retries get 409 request_in_progress; same key + different body = 422 | `tests/adversarial/test_06_same_idempotency_key_creates_one_hold.py` |
| - | A user fires many small holds at once to get past the 10-seat cap | One user hoards a sale | The cap is checked and counted atomically in `reserve_tier.lua` (`uhold`), so concurrent requests can't add up past it | `tests/concurrency/test_user_hold_cap.py` |
| - | A client sends a huge body (or a chunked one with no length, or a fake Content-Length) | Memory and CPU spent parsing junk; easy denial of service | `BodySizeLimitMiddleware` refuses anything over 16 KB with 413 before the app reads it | `tests/unit/test_body_limit.py` |
| 5 | Users create holds and walk away | Seats stay locked forever; the sale looks sold out | Every hold is in `holds:expiry`; the worker's sweeper releases expired holds once per second via the idempotent `release_hold.lua` | `tests/adversarial/test_05_abandoned_hold_returns_inventory.py` |
| - | A hold is released twice (retry, two sweepers, cancel racing the sweeper) | Seats returned twice: phantom inventory, then oversell | Release only acts on a HELD hold and flips its status in the same atomic step | `tests/integration/test_release_hold.py::test_ten_simultaneous_releases_return_the_seats_only_once`, `test_05_...::test_two_sweepers_at_once_never_return_seats_twice` |
| - | A user cancels someone else's hold (forged hold id) | Another user loses their seats | The owner is checked inside the script; a foreign hold gets the same 404 as an unknown one | `tests/integration/test_cancel_hold_api.py::test_someone_elses_hold_looks_like_it_does_not_exist` |
| - | A release fails and the per-user count is never decremented | That user is stuck at the cap | `uhold` can't go negative, and it has a safety TTL (hold TTL + 900 s) refreshed on each reserve | `tests/integration/test_release_hold.py::test_the_user_count_has_a_safety_expiry` |
| 12 | The inventory counter is missing (Redis restart, flush, new tier) | Treated as 0, the sale wrongly shows sold out; treated as capacity, it oversells | NOT_INITIALISED is never zero. The counter is rebuilt from capacity - sold - active holds (- pending orders later) under a single-flight lock, written with SET NX; 503 only if the rebuild can't finish | `tests/adversarial/test_12_missing_counter_is_rehydrated.py` |
| - | Many requests hit a missing counter at once | A stampede of expensive rebuilds, or racing writes | A Redis lock: 1 rebuild for 50 simultaneous requests (measured); the others wait for the result | `test_12_...::test_fifty_simultaneous_requests_rebuild_once_and_never_oversell` |
| 1 | N concurrent holds on C seats (the thundering herd) | Oversell | One atomic Lua script decides availability; refusals are always `sold_out`; Redis and Postgres are checked afterwards. 500 buyers wanting 1-4 seats each on 50 seats, with the counter present or missing at the start (rebuilt mid-rush): never more than 50. The same test **fails** (52 of 50) when the Lua script is swapped for naive check-then-take. Live: 1,000 buyers via 3 separate API processes on 100 seats gave exactly 100 holds (naive: 103) | `tests/concurrency/test_01_concurrent_holds_never_oversell.py`; demo `learning/examples/s2_9/three_replicas_demo.py` (nginx + Docker replicas: S8.1) |
| - | The same hold is confirmed twice (double click, retry, two tabs) | Two orders for one set of seats | `uq_orders_hold_id`: Postgres refuses a second order for the same hold | `tests/integration/test_order_tables.py::test_one_hold_can_become_only_one_order` |
| 4 (schema) | Two ISSUED tickets for one seat or one ticket number | Double sale | Partial unique indexes `uq_tickets_issued_seat` / `uq_tickets_issued_number` (only ISSUED rows count). The full test 4, with Redis wiped, comes in S4.5 | `tests/integration/test_order_tables.py::test_a_seat_can_have_only_one_issued_ticket` |
| 2 | A forged or someone else's hold id is confirmed | Tickets for seats you never held, or a stolen hold | `consume_hold.lua` checks the owner; unknown and foreign holds get the same 404; nothing is charged and the real owner keeps the hold | `tests/adversarial/test_02_forged_or_foreign_hold_gets_nothing.py` |
| 3 | The client sends seat ids, quantity, price, tier or user at confirm | Buying more seats, or paying less | Confirm accepts only `payment_token` (`extra="forbid"`, 422); quantity comes from the server-side hold and price from Postgres | `tests/adversarial/test_03_client_supplied_seats_and_quantity_are_ignored.py` |
| 6 (orders) | Confirm is retried or double-clicked | Two orders and two charges | An Idempotency-Key replay; an existing order is returned for a re-confirmed hold; `uq_orders_hold_id`; the charge key is tied to the hold; 10 concurrent confirms give 1 order | `tests/integration/test_confirm_api.py` (retry, new key, 10 simultaneous) |
| - | Payment fails, or the DB write fails after payment | The customer pays with no order, or loses their seats | The hold reverts to HELD (keeping its original expiry); a payment already taken is refunded | `tests/integration/test_confirm_api.py` (failed payment, saving fails after payment) |
| - | A user exceeds the per-event purchase cap with parallel confirms | More than 10 tickets per user | A pre-check before charging, then a re-check under a `SELECT ... FOR UPDATE` lock on the user's row | `tests/integration/test_confirm_api.py::test_the_purchase_cap_counts_earlier_orders_and_charges_nothing` |
| - | One corrupt entry in a hold index | Every rebuild fails (sale halts with 503s) and every sweeper pass fails | Malformed entries are skipped and logged; the sweeper drops them from the index | adversarial tests 12 and 5 (malformed-entry cases) |
| - | Two relays (or worker replicas) run at once | The same order is published twice, or relays queue behind each other's locks | `SELECT ... FOR UPDATE SKIP LOCKED`: each relay takes only rows nobody else has locked; a row is marked PUBLISHED in the same transaction | `tests/integration/test_outbox_relay.py` (locked row is skipped; 4 concurrent relays publish 200 rows exactly once) |
| - | Publishing one outbox row fails | Every later order waits behind it | Each row is published in its own try/except; the failed row stays PENDING for the next pass | `tests/integration/test_outbox_relay.py::test_one_failing_row_does_not_block_the_others` |
| 8 | A poison outbox row (unpublishable, or always rejected) | Every later order waits behind it forever, or it retries in a tight loop forever | Each row is handled in its own try/except; `PermanentError` goes DEAD at once; other failures back off exponentially and go DEAD after 8 attempts, with `last_error` stored; DEAD rows are never picked up again | `tests/adversarial/test_08_poison_outbox_row_does_not_block_later_rows.py` |
| - | Redis is down for minutes while orders keep arriving | Every pending row burns its attempts and goes DEAD | Connection and timeout errors stop the batch without counting an attempt; rows go out once Redis is back | `tests/integration/test_outbox_relay.py::test_redis_being_down_costs_no_attempts` |
